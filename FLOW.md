# Work flow (automatic; rules for every Claude session)

Repo: **igalgerman/oren_study**, branch **`main`** = what is live on the site. The old repo igalgerman/a (`old` remote) is history only — never push there.
Backlog = GitHub issues. Owner guide: `HOWTO.md`. Main session: `ORCHESTRATOR.md`.

## The flow
idea → `/grill-me` → `/to-tickets` → issue (backlog) → runner → worker → reviewer → merge to main → all tests → deploy → issue closed.
Every issue needs an `## Acceptance` section (3-7 checkable points + the tests that prove them, and `Out of scope`) before `ready-for-agent`; triage writes it. The runner does not start an issue without it (no relabel); once per hour it sends ONE line `add Acceptance lists: #a #b ...` to the inbox window, which writes them. P0, `express` and `bug` issues are exempt (#186). The worker builds exactly that list; the reviewer gives FIX only for a missed Acceptance point, wrong behaviour or a failing test, everything else is a PASS note.
Everything after the issue is automatic (`tools/runner`). Lanes: `local_lanes` on this PC (0 now) + cloud sessions: the usage governor (#239, #274) picks 2-8 so the 5h window ends near `governor_target` (99%) and the week near `governor_week_target` (99%): week projected behind -> 8 lanes, ahead -> max 4; no new run at `governor_stop` (99%)+; no fresh `.runs/usage.json` from the panel -> `remote_lanes` (4)), at most `max_core` (3) `core` issues at once (see `tools/runner/config.toml`). If merging into main conflicts, the runner has the worker merge main in and retries (2 rounds, then the issue is parked).

Hand work by the orchestrator/inspector carries the label `manual`, never `in-progress` and no `core` on tooling: the runner ignores `manual` (no lane, never started) (#177).

Priority: label `P0` (urgent) / `P1` / `P2` (normal, default) / `P3` (low) orders the queue: bugs first, then P0→P3, then oldest.

## If you are a WORKER (window `issue-<n>`, in worktree `wt-<n>`, branch `lane/<n>`)
Do the WHOLE job yourself, then report. Nobody merges for you by hand.
1. Read CLAUDE.md, this file, and the issue (`gh issue view <n> --repo igalgerman/oren_study --comments`). Do only that issue.
2. Implement (use the `mattpocock-skills:tdd` skill: test first; for a bug `mattpocock-skills:diagnosing-bugs`, then tdd). `export PATH=/c/work/Oren_study/bin:$PATH` (python3). In `oren2/`: `python3 build_talents.py`, then the suites you touched
   On the owner's PC: NO game suites / Playwright (`tests/run.sh` and `tests/lib.js` refuse unless `CI=true`, a cloud session or `ALLOW_LOCAL_TESTS=1`, #284); run only the python tool tests you touched. CI runs the suites on the PR.
3. Screenshots of every changed screen at phone 390x844 and desktop 1366x768 into `C:/work/Oren_study/shots/<n>/` (outside the repo: tests/run.sh wipes tests/.tmp); look at them (simple, one main action, Hebrew with nikud).
4. Commit your changes (NOT the built `oren2/index.html` / `oren2/cf/public/index.html`, node_modules, package*.json, tests/.tmp).
5. `git push -u origin lane/<n>`, then **open the PR**: `gh pr create --repo igalgerman/oren_study --base main --head lane/<n>` with `Closes #<n>` (write the body with the `mattpocock-skills:pr` skill), a short summary and the screenshot paths.
6. The very last line of your final message: `RESULT: DONE` (or `RESULT: STUCK <why>`). STUCK goes to the orchestrator (labels `blocked` + `needs-orchestrator`), not to the owner.
7. Need the owner? End your turn with `QUESTION: <short question, options>` — the orchestrator asks him and types the answer back. Unanswered for 30 min: the issue is parked (blocked + ready-for-human: a real owner question), your window stays open, the lane goes to the next issue.
Never push to main, never deploy, never force-push. Found another problem? Open a new issue (see "One backlog, no duplicates" in CLAUDE.md).

## If you are a REVIEWER (window `review-<n>`)
Read-only. Use the `mattpocock-skills:code-review` skill (Standards = CLAUDE.md + FLOW.md, Spec = the issue), then check the PR against the issue: correct, simple (one main action per screen), Hebrew nikud, facts, no unrelated changes. One PR comment; last line one of four colours: `VERDICT: PASS` (green, merge); `VERDICT: PASS-NOTES a; b` (blue: polish only, merges, notes go to the rolling 'Polish backlog (lane)' issue); `VERDICT: PURPLE <question> merge-safe|hold` (owner decision, code works); `VERDICT: FIX <points>` (red: only wrong behaviour, missing/failing test, spec miss, security, data loss, broken build; one-line reason each). Round 2+ checks only the earlier RED points; two fix rounds, the second one with Opus; still RED -> `blocked` + `needs-orchestrator` with all reviews in one comment, never the owner (#303; counted on the dashboard). Cloud issues: the reviewer is a cloud session too and the VERDICT is read from its PR comment; FIX goes back to the worker session (#134, `docs/agents/remote.md`).

## The runner does the rest
On PASS (config `ci_merge = true`, #74, #185): only then the runner marks the PR `gh pr merge --auto --squash` (GitHub merges it when `tests` is green; if GitHub refuses with 'clean status' the runner merges directly) and waits for MERGED; no lock for merging. A FIX verdict, or a PR the runner gives up on, gets `--disable-auto`. Nobody asks the owner to click Merge. The runner finds the PR on `lane/<n>` or on a `claude/*` branch (`remote.pr_for`, #246). It merges main into the lane only when GitHub reports the PR as CONFLICTING (worker resolves) (#166). A red check is rerun once (flaky); still red -> the worker fixes it (same FIX loop). Every wait loop (worker, reviewer, CI merge) also ends the run as DONE when the issue was closed or its lane PR merged elsewhere: lane, locks and `in-progress` are freed, the next pass starts (#234). The merge is tied to the reviewed head (`--match-head-commit`); if the head moved after the PASS (#344): only merges of main (clean, or edits only inside conflict markers) -> the new head counts as reviewed, CI on it, merge; any other new commit -> one quick cloud re-review of the new head, then merge; a draft or a `no-automerge`/`blocked` PR is never merged. No open PR but the issue's PR is already MERGED (by hand or auto-merge): the run ends DONE (#344), not BLOCKED; no PR at all stays rc 4. Backstop (#262): every watchdog tick, an open PR that conflicts with main (dirty) and has auto-merge or a review PASS gets a resolve run by itself (window `resolve-<n>`, `tools/runner/conflicts.py`; one per PR at a time, lane/* and claude/*); two failed rounds -> `blocked` + `needs-orchestrator`; the dashboard shows `PRs with conflicts: N`. No full local suite. Then ONE build + deploy of main (PRs merged back to back share one deploy; pregen only if `pregen = true`), closes the issue and the windows, and starts the next ready issues. `ci_merge = false` or no PR: the old `tools/integrate.sh` (local merge + all tests). On any failure: nothing goes live, the issue gets `blocked` + `needs-orchestrator` with the reason; the orchestrator handles it (the owner only sees `ready-for-human` / `needs-triage`).
Auto-resume (#264): every pass, an open `blocked` issue (not `ready-for-human`/`manual`) whose PR is open is unblocked and restarted at the right step: `resolve` if the PR is dirty, `fix` if the head's VERDICT is red, `merge` if it is PASS, else `review` (no new worker). Before a pass starts issue n it looks up n's open PR (lane/n, claude/*, 'Fixes #n'): if there is one, no new worker, the run resumes at the same step (a PURPLE head is not started) (#295). Max 2 auto-resumes per issue (`.runs/<n>/resumes`), then it stays `blocked` + `needs-orchestrator` (the orchestrator is told once). `ready-for-human` is set only for a real owner QUESTION (or a PURPLE hold); a parked window with no QUESTION, and any old `blocked` + `ready-for-human` without a QUESTION comment, get `needs-orchestrator` instead.

## Lanes
| label | what | parallel |
|---|---|---|
| `core` | touches talents.js / index.html core / reading.js / build_talents.py / wire.js / tests/run.sh | max 3 at a time (`max_core`) |
| `pack` | only inside one pack file + its own test | yes |

Line endings: `.gitattributes` forces LF (`* text=auto eol=lf`). Workers write files with LF (Python: `open(p, "w", newline="\n")`); when merging main into a lane use `git merge -X renormalize origin/main`.

Known: `worker` suite fails only on Windows (ESM c:\ path); `reading`/`activities`/`time-missions` can be flaky under load — rerun alone once.

## Observer
Every `observer_minutes` the watchdog runs `tools/runner/observer.py` (deterministic rules, no LLM): make_ready (needs-orchestrator/P0 untouched 30+ min while the orchestrator is idle), rerun (in-progress with no live run window for 10+ min), fix Blocked-by lines. Max 5 actions per run, each commented on the issue; never on ready-for-human, on an issue with an open lane/<n> PR, or while integrate.lock is alive. Result in `tools/runner/.runs/observer.last`; `observer_minutes = 0` stops it.

One GitHub reader (#329, `tools/runner/ghcache.py`): every minute the watchdog reads GitHub ONCE (one batched GraphQL query: open issues with comments, recent closed issues, recent PRs, lane branches, plus the free rate_limit) into `.runs/gh_cache.json`. Every gh read of the runner passes, the per-lane cloud polls, the panel (60 s, reads the file itself) and the dashboard is answered from it; writes still call gh and mark their issue dirty until the next read. A cache older than 3 min is never used (plain gh instead). A rate-limit answer is retried after Retry-After / 60 s (5 tries), never exits a run or blocks an issue; a run that still cannot read its issue goes back to ready. Dashboard: `GitHub: <calls>/min · graphql left · core left`, ALARM under 20%.

Lane backstop (#248, independent of the runner): every minute the watchdog kills (by herdr address) a live `run-<n>` window whose issue has been CLOSED for 10+ min and that does not hold the merge lock, removes `in-progress`, logs it and tells the orchestrator; a `run-<n>` whose `.runs/<n>` is unchanged for `stuck_hours` gets one alarm, and if still unchanged 30 min later a second one and it counts as a stuck lane (`dashboard.py --text` prints `STUCK LANES`). A gh error reaps nothing.

Parked work (#282, `tools/runner/parked.py`): batch members (`In batch #N`) count under their batch on the dashboard, `manual`/`later` have their own counts. Once an hour the watchdog: a closed batch's still-open members get `ready-for-agent` back (orchestrator told); a `Polish backlog (<lane>)` issue becomes `ready-for-agent` P3 at 5 notes or when its oldest note is 24 h old; a `later`/`manual` issue untouched 2 h+ with no open owner question, no run/PR and no future `until/due YYYY-MM-DD` -> `parked without owner question: #n`. At retro_hour the night report lists every open issue that is not ready-for-agent with its reason; no reason = ALARM.

AI observer (#203): every `ai_observer_minutes` (60; 0 = off) the watchdog starts ONE headless `claude -p --model sonnet` (`tools/runner/ai_observer.py`, read-only tools, 10 min timeout, never two at once). It checks open issues/labels/Blocked-by, open PRs, cloud issues (`remote.py status`), runner/watchdog log tails and the merge lock, and reports at most 5 `OBSERVER: <problem #n> -> <fix, who>` lines (or `no problems`) in `.runs/ai_observer.last`. New findings go to the orchestrator (same issue + text start not again within 6 h); one for the owner also goes to #193. It never edits, merges, labels or comments itself. Issues labelled `cloud` have no local window/worktree by design: neither observer flags that.

Questions to the owner: in Hebrew, through tools/ask/ask.py (browser page), one round at a time; never ask in the terminal when the owner prefers Hebrew.
Every owner question also lands in ONE place: the pinned issue 'Questions for the owner' (#193, `tools/runner/owner_q.py`; the watchdog posts window questions itself); #220: each open question also pops up in a pinned `question-<n>` window: Hebrew page + phone push, first answer wins). Write `QUESTION:` lines in Hebrew, with the options.

## CI (GitHub Actions, #73)
`.github/workflows/tests.yml` runs all suites on every PR to main and every push to main: 6 parallel shards (`SUITES_SHARD=i/6 tests/run.sh`, a failed suite is retried alone once; #187: a suite over its `oren2/tests/budget.txt` seconds fails, a shard over 8 min fails, times in the step summary + artifact for the weekly test gardener `tools/test_garden.py`, which only proposes trims in ONE issue), a `tools` job (runner/watchdog/ask tests with python, panel tests with `node tools/mods/oren-lanes/run-tests.mjs`, #152) and one summary job `tests`. **A PR is mergeable when the `tests` check is green.** No secrets in the tests workflow.
Deploy (#192): `.github/workflows/deploy.yml` runs after `tests` is green on a push to main (newest commit only): build + `deploy.sh` (repo secret `CLOUDFLARE_API_TOKEN`), job summary (ok/fail, URL, D1), live smoke check on the deployment URL + production (`tools/ci/deploy_ci.py smoke`: page, save round trip then deleted, D1 bound, voice status; a worker can run `python3 tools/ci/deploy_ci.py smoke https://oren-game.pages.dev` to verify a fix live, #150), then voice pregen in its own job (own queue: a newer deploy never cancels a running pregen). Every 15 min it also deploys the newest green main if that sha was never tried (marker: Actions cache `deploy-attempt-<sha>`), so cancelled/skipped runs never leave merged work off the site. A failed deploy opens/comments the issue `Deploy failed` (P0). Each deploy is a GitHub deployment (environment `production`); the dashboard reads its deploys from there. The runner no longer deploys (`deploy_in_ci = true`; `false` = old PC deploy with `.env`).
